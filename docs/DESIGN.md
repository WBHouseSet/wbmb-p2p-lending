# WBMB 담보·USDT P2P 대출 — 검토 및 설계 초안

작성일: 2026-10-01 (KST) · 상태: **제품 검토/설계, 미구현·미배포**

이 문서는 사용자 요구, 웹에서 확인한 기존 방식, 새롭게 제안하는 설계를 구분한다. 모든 금리·가격·한도 예시는 설명용이며 실제 시세나 안전성이 검증된 운영 파라미터가 아니다. 이번 작업은 문서 작성이며, 기존 거래 시스템 변경·실자금 거래·GitHub 게시를 수행하지 않는다.

## 1. 결론과 사용자 요구

**양쪽이 조건을 제안하고 소액으로 나누어 체결하는 WBMB 담보 대출은 스마트컨트랙트로 설계할 수 있다.** 정상 상환 시 대출자는 USDT 원금·이자를 받고, 담보 정산 시에는 대출자가 WBMB를 받는다. 사용자가 후속 답변에서 이 수령자를 명시적으로 확인했다. 여기서 대출자는 USDT를 빌려주는 사람, 차입자는 WBMB를 맡기고 USDT를 빌리는 사람이다.

이 상품은 USDT 원금 보장 상품이 아니다. WBMB 지급으로 거래를 끝내면 USDT 회수·매도 부담과 가격 하락 위험을 대출자가 인수한다. 담보 추가·낮은 기준가격·헤어컷도 그 위험을 없애지는 못한다.

| 항목 | 요구/확정 내용 | 설계 해석 또는 미정 사항 |
|---|---|---|
| 접속 | 유니스왑처럼 지갑으로 이용 | 개인키·시드 입력 없이 지갑 연결과 서명 |
| 거래 게시 | WBMB 보유자와 USDT 보유자 모두 제안 | 차입 요청·대출 제안 두 방향 |
| 금리 | 당사자끼리 결정 | 고정 단리 APR로 계약하고 기간 이자 표시를 제안 |
| 담보 평가 | Uniswap 또는 LBank 최근 일주일 최저가 | 정확한 관측 방식과 소스 선택 정책은 추가 설계 필요 |
| 헤어컷 | 낮게 | 숫자는 미정; 낮은 헤어컷은 높은 대출비율을 뜻함 |
| 소액 | 부분 참여·부분 진행 가능 | 게시글을 여러 독립 대출로 나누어 체결 |
| 정산 | 청산 시 대출자가 WBMB 수령 | 가격 하락 청산인지 만기 미상환인지, 초과담보 반환은 미정 |
| 담보/이자 | 추가 담보 및 이자 처리 조사 | 아래 6~8절에 방식·제안 기록 |
| 수익 | 개발자 몫 없음, 이용 수수료 소각 | 공급자 이자와 소각 수수료 분리 |
| 공개성 | GitHub 소스 공개, 글로벌 접근 | 자금 권한·오라클·웹 화면의 의존성도 공개 |

**핵심 미정은 청산 트리거다.** 아래에서는 A안(가격+만기)을 원안에 대한 상세 검토로, B안(만기만)을 별도 대안으로 다룬다. B안으로 원래 요구를 임의 변경하지 않는다.

## 2. 기존 프로토콜에서 확인한 방식

| 사례 | 공식 문서에서 확인한 사실 | 우리 설계에 적용할 점 |
|---|---|---|
| PWN | 양쪽이 조건을 제안하는 P2P 대출. 고정 APR·기간·LTV·최소 대출액 설정. 가격 청산 대신 만기 미상환 시 담보 청구 | 당사자 금리·만기 협상과 담보 인수형 정산에 가까운 비교 사례 |
| Aave | 대출 자산으로 일부/전액 상환. 담보 추가 또는 상환으로 건전성 개선 | 별도 개인키 이자 지갑 없이 승인·상환 트랜잭션 사용 |
| Morpho Blue | 담보 추가·조건부 인출. 일반 청산자는 부채 자산을 지급하고 담보 수령 | 담보 관리 참고. 우리 방식은 대출자에게 직접 WBMB를 귀속하므로 그대로 복제할 수 없음 |

근거: [PWN 설명](https://docs.pwn.xyz/), [PWN 제안 생성](https://docs.pwn.xyz/guides/lending-on-pwn/creating-a-lending-proposal), [PWN 코어 설명](https://github.com/PWNDAO/pwn_dev_docs/blob/main/smart-contracts/core/deep-dive.md), [Aave 상환](https://aave.com/help/borrowing/repay-tokens), [Aave 담보 건전성](https://aave.com/help/borrowing/liquidations), [Morpho 소스](https://github.com/morpho-org/morpho-blue/blob/main/src/Morpho.sol), [Morpho 청산](https://docs.morpho.org/learn/concepts/liquidation/).

PWN 문서는 BNB Smart Chain 배포도 명시한다. 다만 이번에는 배포 주소·코드 버전·WBMB 지원·부분 체결 호환성·실제 유동성·수수료 변경 가능성을 검증하지 않았다. PWN 사용으로 우리 요구가 즉시 충족된다는 결론은 아니다. 기존 코드 재사용 시 라이선스와 원래 프로토콜 수수료도 확인해야 한다.

## 3. 자산과 체인: 현재 저장소에서 확인한 범위

현재 `bot/config.py`(검토 시 HEAD `f63ef46`)에는 다음 설정이 있다.

| 항목 | 설정 |
|---|---|
| 체인 | BNB Smart Chain, chain ID 56 |
| WBMB | `0x9e4c611b834672c3643d9818249366bf65ae4c86`, decimals 8 |
| USDT 표기 토큰 | `0x55d398326f99059ff775485246999027b3197955`, decimals 18 |
| LBank 심볼 | `bmb_usdt` — BMB 가격이며 WBMB 자체 가격이 아님 |
| 직접 DEX 풀 | Uniswap v4, USDT/WBMB, hooks=0 |
| 직접 풀 ID | `0xb840013a7709f266e746bc159e9243bbf664a6885342d23528695b0c51910352` |
| 다른 경로 | USDT→MOVN→WBMB; 각 구간을 같은 시점으로 환산해야 함 |

이것은 현재 로컬 코드 확인이지 오늘의 체인 상태·유동성·토큰 관리권을 재검증한 결과가 아니다. 배포 전에 RPC로 체인·바이트코드·decimals·전송 특성·관리자/동결/업그레이드 권한을 확인해야 한다. 이름이 USDT인 다른 체인 토큰의 6 decimals를 적용하면 안 된다.

`docs/01_assets.md`에는 BMB가 별도 체인이고 WBMB↔BMB 전환은 앱 경로에 의존한다고 기록돼 있다. 따라서 **LBank BMB 가격을 WBMB가 즉시 같은 가격으로 상환·매도 가능하다는 보장으로 쓰지 않는다.** 전환 중단·지연·수수료·디페깅은 별도 위험이다. 이번에 앱의 현재 상환 조건을 실측하지 않았다.

## 4. 지갑 연결과 거래 게시

### 4.1 개인키 없는 로그인

1. MetaMask·Rabby 등에서 지갑 연결, 체인 56 확인.
2. 읽기·조회는 로그인 없이 허용. 오프체인 알림·게시 세션이 필요할 때만 SIWE 메시지 서명.
3. SIWE는 도메인·체인·nonce·발행/만료시각·서명자를 검증하고 nonce 재사용 차단.
4. 로그인 서명, 토큰 사용 승인, 실제 대출 체결은 서로 다른 화면과 동의로 구분.
5. 서버·브라우저 폼에 개인키나 시드를 입력하거나 저장하지 않는다.

일반 방식 근거: [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361). 온체인 거래만 필요하면 별도 로그인 세션 자체가 필수는 아니다.

### 4.2 양방향 게시글

| 게시자 | 예시 | 상대방의 행동 |
|---|---|---|
| 차입자 | “WBMB를 맡기고 최대 900 USDT, APR 12%, 체결일부터 30일, 10 USDT부터” | 대출자가 원하는 일부 금액을 선택 |
| 대출자 | “최대 1,000 USDT 대출, APR 10%, 14일, 담보 정책 X, 10 USDT부터” | 차입자가 일부 금액·필요 WBMB 확인 후 체결 |

게시글 필드: 방향, 작성자, 토큰 주소, 총 USDT 한도, 최소 체결액, 담보 수량 또는 담보율 규칙, APR, 대출 기간, 게시 만료, 가격 정책 ID, 헤어컷, 청산 모드/임계값, 유예기간, 수수료율, 취소 상태. 모든 조건은 체결 전 명시하고 체결 후 일방 변경하지 않는다. 상대 조건을 바꾸고 싶으면 반대 제안으로 새 게시글을 만든다.

초기 제안은 **온체인 게시·예치 방식**이다. 대출자는 게시 한도의 USDT, 차입자는 차입 요청의 WBMB를 주문 에스크로에 잠근다. 취소·게시 만료 시 미체결 잔여분은 작성자가 회수한다. 체결된 담보와 분리하므로 게시 취소가 기존 대출을 취소하지 않는다. 미체결 자금은 이자가 발생하지 않으며 다른 곳에 재예치하지 않는다.

대안은 PWN처럼 체결 전 지갑에 자금을 두는 서명 주문이다. 게시 가스는 줄지만 잔액·승인 철회로 체결 실패할 수 있다. 후속 버전에서 EIP-712 + chainId + verifyingContract + maker nonce + deadline + 누적 체결량 + 온체인 취소를 구현한다. EIP-712 자체는 재사용 방지를 제공하지 않는다. [EIP-712](https://eips.ethereum.org/EIPS/eip-712)

## 5. 소액·부분 체결: 게시글과 대출을 분리

**한 게시글을 여럿이 나누어 채우되, 체결마다 독립된 loanId를 만든다.** 공동 담보를 모든 대출자에게 비례 분배하는 풀은 첫 버전에서 사용하지 않는다.

예시: 차입자가 10 WBMB를 맡기고 최대 900 USDT를 요청한다. A가 90, B가 180 USDT를 제공하면 A 대출에 1 WBMB, B 대출에 2 WBMB가 배정된다. 남은 7 WBMB는 미체결 주문 담보다. 이 숫자는 체결 시 담보 조건을 통과한다는 가정이다.

- 이자와 만기는 각 부분 체결 시점부터 시작한다. 게시한 시점부터 계산하지 않는다.
- 차입 요청의 담보는 원래 한도 대비 비례 배정하되 WBMB 최소 단위로 올림. 마지막 잔여분과 총 예치량을 검사한다. 현재 가격에서 부족하면 체결을 거절한다. 서명한 담보보다 몰래 더 배정하지 않는다.
- 대출 제안은 체결 시 가격 정책에 따라 필요 담보를 계산하고, 차입자가 지정한 `maxCollateral` 이내일 때만 체결한다.
- `fill` 한 트랜잭션에서 미체결량 감소, 담보 배정, USDT 지급, loanId 생성이 함께 성공하거나 전부 되돌아간다.
- A 대출의 상환·추가 담보·청산은 B 대출을 바꾸지 않는다. 추가 담보를 넣을 loanId를 지정한다.
- 대출자는 활성 대출 원금을 중간에 임의 회수할 수 없다. 차입자는 일부 원금/전액 상환 가능하도록 제안한다.
- 첫 버전은 대출채권 양도·NFT화·재담보·자동 롤오버를 제외한다. 웹에서는 관련 대출들을 묶어 보여줄 수 있다.
- 최소 체결액은 작성자 선택 + 컨트랙트의 dust 방지 하한. 예시 10 USDT는 확정값이 아니다. 남은 잔액이 최소액보다 작은 경우 마지막 전량 체결 예외를 명시한다.
- `claim`/상환/정산은 한 loanId 또는 크기 제한 batch로 처리한다. 무제한 참여자 루프를 만들지 않는다.

소액 참여의 한계는 금액 자릿수보다 가스비다. 예컨대 10 USDT·APR 12%·30일 이자는 약 0.098630 USDT에 불과하다. 실제 가스 견적과 기대 이자를 같이 표시하고, ‘적은 금액도 가능’과 ‘경제적으로 유리’를 구분한다.

## 6. 최근 7일 최저가와 낮은 헤어컷 검토

### 6.1 원문 의미와 권장 가격을 구분

**원문 그대로의 가격**은 직전 604,800초 구간의 모든 유효 체결가 중 최저값이다. 달력상 이번 주의 최저가나 7일 평균가가 아니다. 한 거래소의 한 순간 저가 체결도 7일간 영향을 줄 수 있다.

**권장 변경안**은 최근 7일의 검증된 30분 가격 구간 336개 중 최저값이다. DEX는 구간 TWAP, LBank는 검증된 구간 체결 데이터 기반 가격을 사용하는 방식이다. 이것은 ‘순간 체결 최저가’와 다르므로 UI에는 **최근 7일 구간평균 최저가**라고 표시해야 한다. 30분·336개는 설계 후보이며 실측으로 결정한다.

당사자가 유리한 가격만 골라 제출할 수 없게 `pricePolicyId`로 소스와 계산식을 고정한다. 기본 검토안은 DEX와 LBank 조정가격이 모두 유효할 때 낮은 쪽을 사용한다. 한 소스만 쓰는 시장은 별도 정책 ID·위험 표시가 필요하다. 소스 장애 시 더 높은 다른 가격으로 조용히 대체하지 않는다.

```text
P7dex = 지난 7일 유효 DEX 구간가격 중 최저
P7cex = 지난 7일 유효 LBank BMB/USDT 구간가격 중 최저 × WBMB 전환 조정계수
Popen = min(P7dex, P7cex, 현재 검증된 WBMB 가격)
```

전환 조정계수는 1:1 상환을 무조건 가정하지 않는다. 근거를 확보하지 못하면 LBank 가격은 참고용으로만 표시하고, 해당 2소스 정책으로 신규 체결하지 않는다. 이 제한은 서비스 의존성을 드러내는 것이며 자동 탈중앙화라고 표현하지 않는다.

### 6.2 LBank와 Uniswap에서 실제로 필요한 작업

- LBank 공식 API는 OHLCV 캔들을 제공한다. 저가 필드를 이용한 최저가와 종가/평균가격은 다른 통계다. 정확한 이동 7일은 캔들 경계·미완성 캔들·누락·중복·시간대를 처리해야 한다. `week1` 캔들 하나나 `day1` 7개가 정확한 이동 168시간을 의미한다고 가정하지 않는다. [LBank API](https://www.lbank.com/docs/)
- 컨트랙트는 HTTPS API를 직접 호출할 수 없다. LBank 데이터는 수집·검증 후 서명 보고서를 온체인에 올리는 오라클이 필요하다. 여러 서명자를 두어도 원 데이터가 한 거래소라는 의존성은 남는다.
- Uniswap v3는 관측 누적값으로 TWAP을 계산한다. 7일 전체 TWAP 하나로는 ‘7일 구간 최저값’을 알 수 없으므로 구간 기록이 필요하다. [Uniswap v3 가이드](https://developers.uniswap.org/docs/sdks/v3/guides/price-oracle)
- **현재 코드의 풀은 v4이고 hooks=0이다.** v4는 오라클 같은 기능을 훅으로 구현할 수 있게 분리했다. 따라서 기존 풀에 v3 `observe()`와 7일 누적 관측값이 있다고 가정할 수 없다. 과거 로그/아카이브로 재구성하거나 별도 관측·보고 시스템이 필요하다. 기존 풀에 오라클 훅을 나중에 단순 부착한다고 가정해서도 안 된다. [Uniswap v4 백서](https://app.uniswap.org/whitepaper-v4.pdf)
- 공개 호출자가 현재 spot을 찍어 저장하는 단순 sampler는 업데이트 직전 조작·선택적 업데이트에 취약하다. TWAP이라는 이름만 붙여 안전한 오라클로 취급하지 않는다.
- 멀티홉 가격은 같은 구간의 두 구간 가격을 곱해 합성한 뒤 최저값을 취한다. 서로 다른 시각의 두 최저값을 곱한 것을 실제 거래가격이라고 부르지 않는다. 동일 WBMB 유동성을 공유하는 여러 경로는 완전히 독립적인 소스도 아니다.

### 6.3 청산에는 과거 최저가를 그대로 사용하지 않는 제안

신규 대출 한도는 보수적인 `Popen`, 가격 청산은 별도 현재 검증가격 `Phealth`로 계산하는 안을 제안한다. 원래 사용자가 현재 청산가격 공식을 지정한 것은 아니므로 이 부분은 설계 제안이다.

과거 최저가를 계속 청산에 쓰면 잠깐 급락한 기록으로 회복 후에도 청산되거나, 7일 경계에서 가격이 갑자기 뛰는 문제가 생긴다. 반대로 긴 TWAP은 급락 반영이 늦어 대출자가 손실을 볼 수 있다. 현재 가격도 순간 spot 대신 검증 구간값·소스 괴리·유동성·지연 기준을 둬야 한다.

보고서에는 `policyId`, 토큰/풀 ID, 단위, 관측 시작/끝, roundId, 유효기한, 전체 구간 커버리지, 소스 상태, 원자료 해시, 서명자를 포함한다. 미래 시각·오래된 round·재사용 서명·중복 서명자·0 가격을 거부한다. 웹사이트가 임의 숫자를 보내는 것으로 한도가 결정되면 안 된다.

오라클 지연/소스 괴리/유동성 부족 시 신규 대출·담보 인출·가격 청산을 차단한다. **상환·추가 담보·미체결 주문 회수·기존 claim은 계속 허용한다.** 가격이 필요한 만기 정산까지 중단될 수 있다는 가용성 위험은 8절에서 별도로 다룬다.

### 6.4 헤어컷 수식과 의미

```text
h = 헤어컷 (예: 10% = 0.10)
C = 담보 WBMB 수량
Popen = USDT/WBMB
L = 대출 원금 USDT
원금 한도: L <= C × Popen × (1 - h)
LTV = 미상환 원금과 발생 이자의 합 / (C × Phealth)
청산 임계값 = λ (예: 95%)
```

**헤어컷을 낮추면 차입자는 더 빌리지만 대출자의 완충 여유는 작아진다.** 10% 헤어컷이면 90%까지 대출한다. 5% 헤어컷과 95% 청산 임계값은 시작부터 여유가 거의 없어 부적합하다.

또한 만기 예상 이자까지 포함해 `L × (1 + APR × 기간/365일) < C × Phealth × λ`를 만족해야 한다. 원금만 보고 한도까지 빌려주면 가격이 그대로여도 이자 누적으로 청산될 수 있다. 이 검사는 가격 하락을 방어하거나 안전성을 보장하지 않는다. 청산과 별도의 안전 여유 파라미터도 실측 후 결정한다.

예시: 1 WBMB, 가격 100 USDT, 헤어컷 10%, 원금 90 USDT, APR 12%, 30일, λ=95%. 만기 부채는 약 90.887671 USDT이며 청산 경계 가격은 약 **95.671233 USDT/WBMB**다. 가격 하락 약 4.33%에서 경계에 도달한다. ‘헤어컷 10%니까 10% 하락까지 안전’은 잘못된 설명이다.

## 7. 담보 추가와 이자 지갑

### 7.1 담보 추가

`addCollateral(loanId, amount)`로 활성 대출에 WBMB를 추가한다. 차입자 승인·전송 후 해당 대출의 담보만 증가하며 금리·만기·원금은 변하지 않는다. 첫 버전은 차입자만 추가하도록 해 잘못된 제3자 입금의 소유권 혼동을 줄인다.

이미 정산된 대출에는 추가할 수 없다. 가격상 청산 가능하더라도 아직 정산되지 않았다면 추가 가능하게 제안한다. 청산 트랜잭션이 먼저 확정되면 담보 추가는 되돌아간다. UI에서 ‘입금 중’과 ‘담보 반영 완료’를 구분하고 청산 방지 확정을 미리 표시하지 않는다.

**담보 인출은 첫 버전에서 전액 상환 시에만 허용하는 안**을 제안한다. 일반 프로토콜처럼 초과담보 일부 인출을 지원하려면 발생 이자·만기 예상 이자·신선한 가격으로 인출 후 안전성을 검사해야 한다. 담보 추가만으로 만기가 연장되거나 연체 상태가 해소되지는 않는다. 참고 구현은 Morpho의 `supplyCollateral`/`withdrawCollateral`이다. [Morpho 코드](https://github.com/morpho-org/morpho-blue/blob/main/src/Morpho.sol)

### 7.2 일반적인 이자 지급 방식 비교

| 방식 | 작동 | 검토 |
|---|---|---|
| 발생 이자 누적, 사용자가 상환 | 부채를 시간에 따라 계산하고 USDT로 일부/전액 상환 | 초기 권장. 이자용 개인키 지갑 불필요 |
| 이자 준비금 예치 | 차입자가 별도 컨트랙트 잔액을 미리 충전, 규칙에 따라 충당 | 자동화 여지는 있으나 미사용금 반환·잔액 고갈·정산 순서 필요 |
| 주기별 납부 | 매주/매월 납기와 유예를 정함 | 미납 트리거·추가 트랜잭션 때문에 소액에 불리 |
| 만기 일괄 상환 | 만기에 원금·발생 이자 지급 | 간단하지만 대출자는 만기까지 현금 이자 수령을 보장받지 못함 |

Aave는 사용자가 대출 자산을 승인하고 상환 트랜잭션을 보내 일부 또는 전액을 갚는 흐름을 설명한다. 아래 단리·고정 APR·개별 대출별 배분은 우리 설계이며 Aave의 변동금리 계산을 복제하는 것이 아니다. [Aave 상환 안내](https://aave.com/help/borrowing/repay-tokens)

### 7.3 초기 권장: USDT 상환 + 컨트랙트 수령 잔액

```text
차입자 지갑 ── USDT 원금·이자·별도 수수료 ──▶ 대출 컨트랙트
                                              ├─ 대출자 claimableUSDT
                                              └─ 소각용 feeUSDT
```

대출자는 연결한 주소로 `claimUSDT()`를 호출해 수령한다. 운영자 개인지갑이 중간에서 보관하지 않는다. 지급할 USDT가 실제로 들어온 뒤에만 claimable에 기록한다. 화면에는 ‘발생했지만 미납인 이자’와 ‘지금 인출 가능한 USDT’를 분리한다.

지갑 승인만으로 시간이 되면 자동 이체되는 것은 아니다. 컨트랙트 실행에는 누군가의 트랜잭션이 필요하다. 초기에는 사용자가 직접 상환한다. 추후 자동납부는 제한된 준비금·허용량과 keeper 비용·실패 처리까지 설계해야 하며 무제한 승인으로 해결하지 않는다.

### 7.4 APR·APY·부분 상환 규칙

자유롭게 정하는 금리는 계약상 **고정 APR(단리 연이율)**로 제안한다. APY는 복리 재투자를 전제로 하므로 단리 계약의 수익을 APY로 잘못 표시하지 않는다. 사용자가 APY 입력을 원하면 복리 규칙 또는 APR 환산 기준을 먼저 정하고 계약값을 확인받아야 한다.

```text
Δ이자 = 미상환 원금 × APR × 경과초 / 31,536,000
예: 90 × 0.12 × 30/365 = 0.8876712328... USDT
```

- ACT/365 Fixed, 초 단위. 체결 순간부터 시작하고 제안 기본안은 만기에서 이자 누적 중지, 유예 중 추가 벌금 없음.
- 미납 이자에 다시 이자를 붙이지 않는다. APR=0도 유효하며 과도한 APR·기간·산술 범위에는 명시적 한도가 필요하다.
- `repay(loanId, principalToRepay, maxTotalUSDT)`는 그 시점의 발생 미납 이자 전액, 그 이자에 대한 수수료, 선택한 원금을 한 번에 받는다. `principalToRepay=0`이면 이자만 납부한다.
- 부분 상환 후 다음 이자는 줄어든 원금에 대해서만 발생한다. 이미 지급한 이자를 다시 더하지 않는다.
- 조기 상환은 실제 경과기간 이자만 납부하는 안을 제안한다. 대출자가 기대한 전체 기간 이자 수익이 보장되는 계약은 아니다.
- 정산 전이면 만기/유예 후에도 상환 허용. 부분 상환은 남은 원금의 만기 미상환 상태를 해소하지 않는다.
- 정수 나눗셈의 나머지를 보존해 작은 반복 호출로 이자를 없애거나 올림 이자를 반복 부과하지 않도록 한다. 최종 정산 시의 최소 단위 처리까지 테스트한다.
- 웹 견적과 블록 확정 사이 이자가 늘 수 있으므로 `maxTotalUSDT` 상한과 전액 상환용 함수가 필요하다. 남은 먼지 부채 때문에 담보가 영구 잠기지 않게 한다.

## 8. 청산 대신 ‘WBMB 담보 정산’

### 8.1 선택해야 하는 두 상품

| 구분 | A: 가격 하락 + 만기 미상환 | B: 만기 미상환만 |
|---|---|---|
| 가격 오라클 | 체결·건전성·담보 분배에 지속 필요 | 참고가격/체결 보조로 한정 가능 |
| 가격 급락 | 정해진 임계값을 넘으면 WBMB 정산 가능 | 만기까지 유지 |
| 차입자 | 가격 청산 위험을 관리해야 함 | 가격 하락만으로 담보를 잃지 않음 |
| 대출자 | 일찍 담보 인수 가능하나 회수액 보장 없음 | 가격 하락·전략적 미상환 위험을 만기까지 부담 |
| 유사 사례 | 일반 DeFi 건전성 판정을 변형 | PWN의 만기형에 더 가까움 |

**탈중앙화 단순성은 B가 유리하지만 낮은 헤어컷과 결합하면 대출자가 부담할 손실이 커질 수 있다.** 차입자는 가격이 오르면 상환하고, 많이 떨어지면 담보를 포기할 경제적 유인이 생긴다. 높은 APR도 이를 확실히 보상하지 않는다.

B에서 전체 담보 귀속을 선택하면 가격 오라클 없이 정산할 수 있지만, 소액 잔여 부채 때문에 많은 담보가 넘어가거나 추가 담보도 전부 귀속될 수 있다. 따라서 B의 초과담보 반환 규칙까지 확정하지 않고 A와 혼합 구현하지 않는다. 가장 작은 첫 시제품으로는 B의 고정 만기·담보 수량 계약을 검토할 수 있으나 사용자 선택이 필요하다.

### 8.2 A안의 구체적인 정산 제안

트리거는 `D / (C × Phealth) >= λ` 또는 `현재시각 >= 만기 + 유예`이고, D는 미상환 원금 + 미납 발생 이자다. 경계의 >= 여부를 컨트랙트와 UI에서 통일한다. 유예는 만기 미상환에만 적용하며 가격 청산에는 자동 유예를 가정하지 않는다.

**대출자가 필요한 담보만 받고 초과분은 차입자에게 반환하는 안**을 제안한다. ‘대출자가 WBMB를 받는다’는 요구는 확정됐지만 ‘전부 가져간다’는 요구는 없었다.

```text
Q대출자 = min(C, ceilWBMB(D / Psettle))
Q차입자 = C - Q대출자
Psettle = 정산에 사용 가능한 현재 검증가격 (7일 최저가가 아님)
```

초기안은 추가 청산 보너스 0, 부채에 소각 수수료를 추가하지 않는다. 별도 keeper 보상을 둘 경우 원래 합의한 재원·상한에서 지급하며 개발자 수익 0 정책과 별도로 공개한다.

정산 한 번으로 대출 상태를 `SETTLED_IN_WBMB`로 종료하고, USDT 청구권을 다시 행사하지 못하도록 한다. 부족분은 대출자가 부담하며 다른 대출·예치금으로 메우지 않는다. 이는 컨트랙트 내부 정산 설계이고 법률상 채무 소멸 효력을 단정하는 문구가 아니다.

예시(1 WBMB, D=90.8876712328 USDT):

| 정산 가격 | 대출자 WBMB | 차입자 반환 WBMB | 의미 |
|---|---:|---:|---|
| 95 USDT | 0.95671233 | 0.04328767 | 8 decimals 올림. 현금 USDT 지급은 없음 |
| 70 USDT | 1.00000000 | 0 | 표시가격 기준 부채 대비 약 20.887671 USDT 부족 |

70 USDT는 오라클 평가액일 뿐 실제 매도 보장액이 아니다. 수령 이후 더 하락하거나 매수 유동성이 없어질 수 있다. 대출자 화면은 ‘USDT 상환 완료’가 아니라 **‘WBMB로 정산: 수령 수량 X, 평가시각 Y’**로 표시한다.

### 8.3 실행·실패·경합

- 누구나 유효 조건에서 `settle(loanId)`를 호출할 수 있지만 자산은 고정된 대출자·차입자의 claimable 잔액으로만 배정한다. 호출자가 담보를 가져가지 않는다.
- 컨트랙트가 스스로 시간을 감지해 트랜잭션을 보내지는 않는다. 대출자의 직접 호출/독립 keeper가 필요하다. 보상이 없으면 소액 건 정산이 지연될 수 있다.
- 담보·부채·미납 이자를 같은 상태에서 확정하고, 정산 이후 이자 중지·재정산 차단·대출별 잔액 제거를 먼저 수행한다. 실제 토큰 수령은 각자 `claimWBMB()`로 가능하게 한다.
- 전액 상환이 먼저 확정되면 정산 불가. 담보 추가/부분 상환이 먼저 확정되면 최신 값으로 조건을 재평가한다. 가격이 회복해 조건을 벗어났으면 이전 관측값으로 청산하지 않는다.
- 오라클 장애 시 A의 강제 WBMB 분배는 멈춘다. 만기가 지나도 정확한 초과담보 분배를 위해 유효 가격이 필요하다. 장애가 영구화되면 정산 지연이 장기화될 수 있다.
- 오래된 가격·운영자 임의가격·담보 전부 몰수로 장애를 조용히 우회하지 않는다. 양측 서명 합의 정산이나 사전에 고정한 대체 정책은 후속 설계 대상이다. **A안의 오라클 영구 장애 처리 정책은 실자금 출시 전 미해결 항목이다.**

## 9. 수수료 전액 소각과 개발자 수익 0

대출자에게 약속한 이자는 전액 지급하고, 차입자가 납부한 이자에 별도 비율 f를 곱한 프로토콜 수수료를 받는 안을 제안한다. `f`는 계약에 고정하며 개발자 수취 주소를 두지 않는다.

예: 원금 90, 30일 이자 0.8876712328, f=5%라면 수수료 0.0443835616, 총 상환 90.9320547945 USDT. **5%는 대출원금의 5%가 아니라 지급 이자의 5%**이며 예시일 뿐이다. 대출자 수령은 원금+이자 90.8876712328 USDT다.

수수료 USDT는 별도 잔액으로 누적하고 충분한 규모에서 WBMB를 매입해 소각/영구 잠금하는 모듈로 분리한다. 매입 실패 때문에 정상 상환·담보 반환을 막지 않는다. 미납 이자나 WBMB 정산 건에서 현금 수수료를 받은 것처럼 기록하지 않는다.

- 소각 모듈은 대출 원금·담보·대출자 claimable을 사용할 수 없다.
- 허용된 토큰·라우터·경로만 사용. 외부 호출자가 임의 calldata/수령 주소/무제한 승인으로 잔액을 빼갈 수 없게 한다.
- 매입 최소 수령량·기한·가격 검증·회차 한도 필요. 누구나 호출 가능하더라도 호출자가 최소 수령량을 0으로 정할 수 없어야 한다.
- WBMB에 공급량을 줄이는 `burn()`이 실제 존재하는지 확인해야 한다. 특정 주소 전송은 `totalSupply` 감소와 다를 수 있다. WBMB를 없애도 원본 BMB가 함께 소각된다는 보장은 없다.
- 정확한 문구는 검증 결과에 따라 ‘WBMB 소각’ 또는 ‘회수 불가 주소로 이전’. 매입 예정·매입 완료·이전/소각 완료를 따로 공개한다.
- 개발·감사·RPC·가격 보고·keeper·가스 비용 재원은 별도로 필요하다. 가스도 수수료에서 공제한다면 ‘수수료 전액 소각’이라는 표현을 수정해야 한다.

이전 거래 시스템의 자금·서명키·실행 프로세스와 분리된 새 프로젝트로 구현한다. 컨트랙트 배포 주소·소스 검증·설정·관리권·소각 이벤트를 공개할 수 있어야 한다.

## 10. 컨트랙트 구성과 상태

아래는 구현을 위한 제안 인터페이스이며 실제 코드/감사 완료 상태가 아니다.

| 구성 | 책임 |
|---|---|
| `P2PLending` | 게시 에스크로, 부분 체결, loan별 담보/부채/이자, 상환, 정산, 수령 잔액 |
| `PricePolicy` | 고정된 소스·보고서 검증 규칙, 가격/유효성 제공; 자금 이동 권한 없음 |
| `FeeBurner` | 수수료 잔액만 매입·소각; 대출 상태 변경 권한 없음 |
| 웹·인덱서 | 이벤트 검색·알림·거래 생성; 서명/자금 통제 없음 |

```text
게시글: OPEN → PARTIALLY_FILLED → FILLED
                  └─ CANCELLED / EXPIRED (미체결 잔액만 회수)

각 체결: ACTIVE → REPAID
             └─ SETTLED_IN_WBMB
```

함수 후보: `createBorrowOffer`, `createLendOffer`, `cancelOffer`, `withdrawUnfilled`, `fillOffer`, `addCollateral`, `repay`, `repayAll`, `settle`, `claimUSDT`, `claimWBMB`.

loan 필드: 원 게시 ID, 양측 주소, 최초/잔여 원금, 담보 수량, APR, 발생 미납 이자와 계산 나머지, 마지막 이자 시각, 체결시각, 만기, 유예, 정책 ID, 청산 임계값, 수수료율, 정산 모드, 종료 상태.

핵심 불변조건:

1. 실제 WBMB 잔액 ≥ 미체결 담보 + 활성 대출 담보 + WBMB 수령 잔액 합계.
2. 실제 USDT 잔액 ≥ 미체결 대출자 자금 + USDT 수령 잔액 + 미이전 수수료 합계. 대출 중인 원금은 컨트랙트 잔액에 있는 것으로 세지 않는다.
3. 하나의 담보 단위가 여러 loan에 중복 배정되지 않는다. 주문 한도 초과 체결 불가.
4. 모든 자금 전송·상태 변경은 원자적. 실패 후 금액만 줄거나 loan만 생성되는 상태 불가.
5. `REPAID`/`SETTLED_IN_WBMB` 이후 이자·정산·상환 재실행 불가. 이미 확정된 claim은 허용.
6. WBMB 8자리·USDT 18자리·가격 스케일을 분리한 정수 산술. 담보 배정/정산 올림과 잔액 보존을 일관되게 처리.
7. 기존 계약의 금리·청산·수수료·오라클 정책을 관리자 일방 변경하지 않는다. 비상 권한을 둔다면 신규 체결 차단 범위 등 정확히 명시한다.
8. 대출자 USDT 손실을 다른 사람 자산으로 보전하지 않는다. 높은 WBMB 평가액을 USDT 원금 회수로 간주하지 않는다.

구현 시 SafeERC20·재진입 방지·상태 갱신 순서·허용 토큰 검증을 적용한다. fee-on-transfer/rebase 등 예상과 다른 잔액 변화는 첫 버전에서 허용하지 않는다. 토큰 전송 실패는 전부 revert하거나 수령 잔액을 보존해야 한다. 일반 라이브러리 사용만으로 대출 로직의 안전성이 확보되지는 않는다. [OpenZeppelin ERC20](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20), [OpenZeppelin Utils](https://docs.openzeppelin.com/contracts/5.x/api/utils)

## 11. 화면과 확인해야 할 시나리오

사용자 화면은 ‘빌리기 / 빌려주기 / 내 거래 / 소각 내역’으로 나눈다. 게시 카드에 APR·기간 이자·수수료·필요 WBMB·현재 청산 경계·가격 산출 방식·부분 체결 잔여액을 표시한다. ‘APY 높음’만으로 정렬하지 않고 청산 시 수령 자산을 함께 표시한다.

체결 확인에는 ‘정상 종료: USDT 원금+이자 / 담보 정산: WBMB 수령, USDT 손실 가능’을 표시한다. 차입자에게는 ‘담보 반환은 상환 후 / 추가 담보는 만기 연장이 아님’을 표시한다. 잔액 조회·예치 승인·실제 체결·미확정 거래 상태를 혼동하지 않는다.

구현 이후 필요한 검증:

| 분야 | 시나리오 |
|---|---|
| 부분 체결 | 같은 잔여분 동시 체결, 취소 경합, 마지막 dust, 다수 소액, 담보 반올림 |
| 이자 | 0 APR, 같은 블록, 만기 경계, 반복 소액, 부분 원금 상환, 조기 상환, 과납 상한 |
| 담보 | 잘못된 소유자, 8/18 decimals, 추가 담보 vs 정산 경합, 다른 loan 담보 사용 차단 |
| 가격 | 7일 경계, 순간 저가, 소스 괴리, 거래 중단, 0/음수/미래값, 누락 구간, 오래된 보고서 |
| 조작 | 낮은 유동성 가격 누르기/올리기, 오라클 보고 직전 조작, 동일 자금 순환 대출, 서명자 담합 |
| 정산 | 임계값 정확한 경계, 초과담보 반환, 담보 부족, 만기 유예, 회복 후 정산 거부, 이중 정산 |
| 자금 | 재진입, ERC20 false/revert, 수령 실패, 공급자 원금과 수수료 분리, 잔액 보존 |
| 서명/웹 | 잘못된 체인·도메인, nonce 재사용, 취소·계정 변경, 연결만으로 자동 승인하지 않음 |
| 소각 | 스왑 실패해도 상환 가능, 원금 접근 불가, 최저 수령량 우회, 동일 회차 중복 집행 |

검증 순서는 수학 모델 → 단위/불변조건 테스트 → 실제 토큰 특성을 반영한 로컬 fork → 테스트넷 지갑 흐름 → 독립 검토다. 로컬 fork·mock 성공은 실제 공급자 모집이나 메인넷 대출 실행 증거가 아니다.

## 12. 구현 전에 결정할 항목과 이번 검토의 한계

| 결정 항목 | 문서의 제안/현재 상태 |
|---|---|
| 청산 트리거 | A(가격+만기) 또는 B(만기만), 아직 사용자 미확정 |
| 초과담보 | A는 필요한 만큼 대출자 귀속, 나머지 차입자 반환 제안 |
| 가격 | 원시 최저체결가 대신 검증된 7일 구간 최저가 제안, 미확정 |
| 헤어컷/임계값 | 낮게 설정하되 숫자는 실측 필요. 10%/95%는 설명용 |
| 기간/최소금액 | 게시자가 선택, 시스템 상한·하한은 가스/위험 실측 후 |
| 이자 | 고정 단리 APR, 실제 경과기간, 만기에서 중지 제안 |
| 담보 추가/인출 | 추가 허용, 첫 버전 중도 인출 제외 제안 |
| 수수료 | 지급 이자의 별도 비율, 개발자 배분 0, 매입·소각 비동기 |
| 글로벌 의존성 | 컨트랙트·화면 공개뿐 아니라 가격 보고자·WBMB 상환·USDT 토큰 관리권 공개 필요 |

다음 구현 단위는 **WBMB/USDT mock 토큰 + 양방향 온체인 게시 + 독립 부분 체결 + 고정 APR + 담보 추가 + 상환/수령**이다. 청산 모드와 오라클 정책이 확정되기 전 실자금 청산 컨트랙트를 완성품으로 배포하지 않는다. 사용자 요구가 이번에는 ‘검토와 문서 작성’이므로 이 문서에서 구현으로 범위를 확장하지 않았다.

이번에 확인한 것은 공식 웹 문서와 현재 저장소 설정이다. 실제 7일 가격 수집, 깊이·조작 비용 분석, 토큰 burn 함수/관리권, 가스비, 외부 대출자 수요, 실제 지갑·체인 거래는 검증하지 않았다. 법률상 서비스 분류도 이 설계 문서로 확정되지 않는다.

문서 검증: Python `Decimal`로 30일 이자·청산 경계·WBMB 올림/잔여담보·부족분·수수료 포함 상환·부분 체결 배분의 9개 수치 검사를 통과했다. 문서 절 구조·코드 블록·링크 형식도 확인했다. 이는 설명용 수학 검증이며 스마트컨트랙트 테스트가 아니다.
