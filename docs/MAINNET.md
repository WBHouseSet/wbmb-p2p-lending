# 실전(BSC 메인넷) 배포 안내

작성일: 2026-10-01 · 대상: 이 프로젝트를 실제 자금으로 처음 띄우는 운영자

이 문서는 첫 실전 버전의 범위, 배포 전 확인한 사실, 배포 순서, 그리고 아직 남은 위험을 적는다. 외부 보안 감사는 받지 않았다. **잃어도 되는 소액으로만 시작한다.**

## 1. 첫 실전 버전이 하는 일

- **가격 오라클 없음.** 게시자가 대출 한도와 담보 수량을 직접 정한다(예: 900 USDT에 10 WBMB). 체결은 그 비율대로만 된다.
- **만기만 정산.** 가격이 내려가도 청산되지 않는다. 만기 + 유예 1일이 지나도록 갚지 않으면 남은 담보 전부(추가 담보 포함)가 대출자에게 넘어간다.
- **수수료는 이자의 5%, 차입자가 이자에 더해 낸다.** 소각하지 않고 수수료 지갑에 보관한다. 수수료 지갑은 배포 시 고정되며 기본값은 배포 지갑이다.
- 양방향 게시, 부분 체결, 단리 APR, 담보 추가, 부분·전액 상환, 각자 수령은 로컬 버전과 같다.
- 컨트랙트에는 관리자·업그레이드·임의 인출·수수료율 변경 기능이 없다. 문제가 생기면 고칠 수 없고 새로 배포해야 한다.

가격 하락 청산(A안)과 서명 가격 오라클(`SignedPricePolicy`)은 이 버전에서 쓰지 않는다. 이유는 2절의 유동성이다.

## 4. 배포 순서

배포 지갑에는 가스비용 BNB만 조금 있으면 된다(0.005 BNB면 충분). 키 파일에는 16진수 개인키 또는 니모닉 한 줄을 넣는다. 스크립트는 키를 출력하거나 저장하지 않는다.

```bash
# 1) 리허설: 아무것도 전송하지 않는다
npm run rehearse

# 2) 예상 비용과 지갑 확인: 아무것도 전송하지 않는다
DEPLOYER_KEY_FILE=/경로/키파일 npm run deploy:bsc

# 3) 실제 배포: 실제 BNB를 쓴다
DEPLOYER_KEY_FILE=/경로/키파일 npm run deploy:bsc -- --broadcast

# 4) 실전용 웹 파일 생성 → dist-live/
npm run build:live
```

- 키 파일이 니모닉이면 지갑 순번과 주소를 함께 지정해야 한다. 스크립트는 서명 지갑이 그 주소가 아니면 아무것도 보내지 않는다. 같은 니모닉의 첫 번째 지갑(다른 용도로 쓰는 지갑)이 실수로 서명하는 것을 막기 위해서다.
  ```bash
  DEPLOYER_KEY_FILE=/경로/키파일 DEPLOYER_INDEX=1 DEPLOYER_EXPECT=0x두번째지갑주소 npm run deploy:bsc
  ```
- 수수료 지갑을 따로 두려면 `FEE_WALLET=0x…`를 함께 준다. 배포 후에는 바꿀 수 없다.
- 3번이 끝나면 `deployments/bsc.json`에 컨트랙트 주소·거래 해시·생성자 인자가 기록된다. 스크립트는 배포된 컨트랙트의 설정을 다시 읽어 예상과 다르면 실패로 처리한다.
- `dist-live/`는 정적 파일이다. 아무 정적 호스팅에 올리면 된다. 화면은 접속 시 컨트랙트의 실제 설정(오라클 없음, 수수료 지갑, 토큰 주소)이 설정 파일과 같은지 확인하고 다르면 열리지 않는다.
- 빌드에는 시장·토큰·수수료 지갑 주소와 함께 **RPC 주소**(`BSC_RPC_URL`, 기본값 `https://bsc-dataseed.binance.org`)도 박힌다. `deployment.json`의 `rpcUrl`이 빌드에 박힌 값과 다르면 화면이 열리지 않으므로, RPC 주소를 바꾸려면 파일만 고치지 말고 `BSC_RPC_URL=새주소 npm run build:live`로 다시 빌드해 올린다. 카운슬 가격형 빌드도 같다.

## 5. 첫 실거래 점검 순서 (소액)

1. 지갑 두 개에 각각 소량의 BNB(가스), 한쪽에 WBMB, 다른 쪽에 USDT를 준비한다.
2. 차입 요청 게시 → 다른 지갑으로 일부 체결 → `deployments/bsc.json`의 주소를 BscScan에서 열어 이벤트 확인.
3. 이자만 납부 → 일부 상환 → 전액 상환 → 담보 수령 → 대출자 USDT 수령.
4. 수수료 탭에서 수수료 이동 → 수수료 지갑 잔액 확인.
5. 기간 1일짜리 대출을 하나 만들어 갚지 않고 만기 + 유예 1일(총 2일) 뒤 정산 → 대출자 WBMB 수령. 화면은 일 단위 기간만 받는다.
6. 미체결 게시글 취소 → 잔여분 수령.

각 단계에서 화면의 숫자와 BscScan의 토큰 이동이 같은지 본다.

## 7. 남은 위험

- **감사 없음.** 테스트가 통과했다는 것과 버그가 없다는 것은 다르다. 컨트랙트는 고칠 수 없으므로 버그가 있으면 예치된 자금이 묶이거나 잃을 수 있다.
- **WBMB 추가 발행.** 소유자 지갑이 WBMB를 더 찍으면 담보 가치가 떨어진다. 컨트랙트로는 막을 수 없다.
- **토큰 관리 권한.** USDT·WBMB 운영자가 전송을 막거나 규칙을 바꾸면 수령이 실패할 수 있다.
- **담보 환금성.** 2절 참조.
- **전략적 미상환.** 가격이 크게 내리면 차입자는 갚지 않고 담보를 포기하는 편이 유리하다. 대출자가 담보 비율로 감수해야 하는 위험이다.
- **부분 상환 후 미상환.** 일부만 갚고 만기를 넘기면 남은 부채가 작아도 담보 전부가 넘어간다.
- **법률.** 서비스가 어느 나라에서 어떤 규제를 받는지 검토하지 않았다.

## 8. 카운슬 가격형 시장

작성일: 2026-10-02 · 상태: **코드와 테스트만 끝났고 아무것도 배포하지 않았다.** 이 절의 명령은 모두 사용자가 직접 지시했을 때만 실행한다. 1절~7절의 오라클 없는 시장(`0xC290…EF73`, 테스트 시장 `0x6A94…D57c`)은 그대로 두고, 이 시장은 **새 주소로 따로 배포**한다.

### 8.1 이 시장이 하는 일

- **모빅 카운슬 가격으로 청산한다.** 카운슬 가격은 투표로 정해지므로 얕은 시장에서 거래로 움직일 수 없다. 대신 가격이 주 2~3회만 바뀐다. 가격 출처는 `https://movnvote.com/api/public/price/latest` 이고, 이 값을 온체인 가격 컨트랙트(`CouncilPricePolicy`)에 옮겨 적는 **중계 봇**이 따로 필요하다.
- **화면은 담보 가치의 60%까지만 빌려주고, 부채가 담보 가치의 80%에 이르면 청산한다.** 화면으로는 이 조건(담보 여유 40%, 청산선 80%, 가격 청산, 유예 1일)만 낼 수 있다. 컨트랙트는 다른 값(담보 여유 1~90%, 청산선은 `1 − 담보 여유`보다 높기만 하면 됨)도 받으므로 누군가 컨트랙트를 직접 호출해 다른 조건의 게시글을 올릴 수 있다. 화면은 그런 게시글을 **빌리기·빌려주기 목록에 보여 주지 않고 체결하지도 않는다.** 올린 사람의 "내 거래"에만 `비표준 조건` 표시와 함께 나와 회수할 수 있다. 화면을 거치지 않고 컨트랙트를 직접 호출하는 사람은 이 보호를 받지 못한다.
- **체결 전에 청산 조건을 보여 준다.** 게시글 카드에 담보 여유와 청산선이 나오고, 체결 확인창에 청산선, 이번 체결에 배정되는 담보로 계산한 청산 가격, 정산되면 대출자가 부채 + 보너스(컨트랙트에서 읽은 값)만큼의 WBMB를 받고 나머지는 차입자에게 돌아간다는 것이 나온다.
- **청산되면 대출자는 부채 + 5%만큼의 WBMB만 받고, 나머지 담보는 차입자에게 돌아간다.** 담보가 모자라면 담보 전부가 대출자에게 간다. 5%는 카운슬 가격이 시세보다 높게 남았거나 받은 WBMB를 팔 때 생기는 손실을 메우는 보너스다. 만기 + 유예가 지난 대출도 같은 방식(가격으로)으로 정산한다. 가격으로 정산이 끝나면 부채 채권은 종료된다.
- **담보를 더 넣을 수 있다.** 청산선에 가까워지면 담보를 추가해 피한다. 대출 카드에 청산 가격(이 가격 아래로 내려가면 청산)과 `청산까지 여유`가 표시된다.
- **새로 대출을 받을 때 쓰는 가격은 보수적이다.** 가격이 바뀐 뒤 12시간(테스트 시장 5분) 동안은 직전 가격과 새 가격 중 낮은 쪽으로 담보를 계산한다. 가격이 막 오른 직후 그 값으로 바로 빌리는 것을 막는다.
- **가격이 멈추면 7일 뒤 풀리는 탈출구가 있다.** 가격이 만료돼 정산 가격을 못 얻는 상태가 계속되면, 아래 두 시각 중 **늦은 쪽**에서 7일(`staleSettleDelay`, 테스트 시장은 5분)이 지난 뒤 담보 **전부**가 대출자에게 넘어간다.
  - (a) 그 대출의 유예 종료(만기 + 유예)
  - (b) 가격의 유효기한(`validUntil`)

  기한만 기준으로 하면 오래 연체된 대출은 중계가 잠깐만 멈춰도 차입자의 초과 담보가 통째로 넘어가기 때문에 (b)도 함께 본다. 가격이 살아 있는 동안은 언제나 가격으로 정산한다. 화면은 이 규칙과 컨트랙트에서 읽은 대기 시간을 보여 준다.

- 가격이 멈춘 동안에도 **상환·담보 추가·게시 취소·수령은 된다.** 멈추는 것은 새 체결과 가격 기반 정산뿐이다.
- 그 밖에는 오라클 없는 시장과 같다. 수수료는 이자의 5%를 차입자가 추가로 내고, 최소 기간 1시간, 유예 하한 1일(가격형도 유예가 하한 미만인 게시는 거부), 관리자·업그레이드·수수료 변경 기능이 없다.

고정되는 값(배포 후 변경 불가): 보고자 1명·서명 1개, 가격 유효기간 최대 6일, 한 번에 최대 30% 변동, 가격 변경 간격 12시간, 보너스 5%, 가격 중단 대기 7일. 테스트 시장은 최소 기간·유예·가격 변경 간격·가격 중단 대기가 모두 5분이고 나머지는 같다.

### 8.2 배포 순서

배포 지갑에는 가스비용 BNB만 있으면 된다. **`REPORTER`는 중계 봇이 서명할 지갑의 주소여야 한다.** 틀린 주소를 넣으면 그 시장은 가격을 영영 받을 수 없고, 고칠 수 없어 새로 배포해야 한다. 아래 표시를 보고 어떤 명령이 BNB를 쓰는지 확인한다.

```bash
# 처음 한 번 (새로 받은 저장소): 컴파일. 배포와 중계가 artifacts/ 를 읽는다. 전송 없음
npm run compile

# 예상 비용만 (전송 없음)
REPORTER=0x중계지갑주소 npm run deploy:bsc -- --council --test-market

# 실제 배포 (BNB 사용, 거래 2건)
DEPLOYER_KEY_FILE=/경로/키파일 DEPLOYER_INDEX=0 DEPLOYER_EXPECT=0x배포지갑 FEE_WALLET=0x수수료지갑 REPORTER=0x중계지갑주소 npm run deploy:bsc -- --council --test-market --broadcast

# 첫 가격 등록: 드라이런 (전송 없음) → 전송 (BNB 사용)
RELAY_KEY_FILE=/경로/중계키 npm run relay:council -- --test-market
RELAY_KEY_FILE=/경로/중계키 npm run relay:council -- --test-market --broadcast
```

- 본 시장은 `--test-market`을 빼면 된다(`--council --broadcast`). 먼저 테스트 시장에서 확인하고 본 시장을 배포한다.
- 예상 비용 실행 예(2026-10-02, 가격 컨트랙트 + 시장): 약 430만 gas, 0.05 gwei 기준 약 0.0002 BNB. 실제 가스 가격에 따라 달라진다.
- 배포는 **거래 두 건**이다. 가격 컨트랙트를 먼저, 시장을 그다음에 올린다. 두 번째가 실패하면 가격 컨트랙트 주소는 실행 로그에만 남으므로 로그를 지우지 않는다. 이 경우 기록 파일은 만들어지지 않으므로(기록은 시장 설정을 다시 읽어 확인한 뒤에만 쓴다) 같은 명령을 다시 실행하면 가격 컨트랙트부터 새로 올리고 그다음 시장을 올린다. 버려진 가격 컨트랙트는 자금을 보관하지 않고 어떤 시장도 가리키지 않으므로 해가 없다. 다만 두 번째 거래가 "확정 대기"에서 멈췄거나 "설정이 예상과 다르다"는 오류였다면, 다시 배포하기 전에 로그에 찍힌 시장 거래 해시를 BscScan에서 열어 이미 올라갔는지 확인한다.
- 성공하면 `deployments/bsc-council-test.json`(본 시장은 `bsc-council.json`)에 주소·거래 해시·생성자 인자가 기록된다. 스크립트는 올라간 컨트랙트의 설정을 다시 읽어 예상과 다르면 실패로 처리한다.
- 키 파일·`DEPLOYER_INDEX`/`DEPLOYER_EXPECT` 규칙은 4절과 같다. 키는 출력·저장되지 않는다.
- **배포가 끝나면 웹 파일을 만들기 전에 중계 드라이런부터 실행한다**(위 명령의 `--broadcast` 없는 줄). 드라이런은 중계 키의 지갑이 가격 컨트랙트의 보고자인지 확인하고, 아니면 `이 지갑은 가격 컨트랙트의 보고자가 아닙니다`로 끝난다. `REPORTER`를 맞게 넣었는지 확인하는 수단은 이것뿐이다. 여기서 실패하면 그 시장은 쓸 수 없으니 화면을 만들지 말고 새로 배포한다.
- 웹 파일 생성(전송 없음): `npm run build:live:council` 은 `deployments/bsc-council.json` 으로 `dist-live-council/` 을 만든다. 테스트 시장은 `RECORD=deployments/bsc-council-test.json OUT_DIR=dist-live-council-test node scripts/build-live.mjs`. 빌드에는 시장 종류·시장 주소·가격 컨트랙트 주소·RPC 주소가 박힌다. 다른 시장 종류나 다른 가격 컨트랙트, 다른 RPC 주소를 가리키는 `deployment.json` 이면 화면이 열리지 않는다(RPC 주소를 바꾸려면 4절처럼 다시 빌드한다).

**첫 가격이 올라가기 전에는 이 시장에서 어떤 게시도 체결되지 않는다.** 가격 컨트랙트에 보고서가 없으면 가격 조회가 실패하기 때문이다. 이 동안 화면은 가격 칸에 숫자 대신 `가격 미등록`을 보여 주고 체결을 막는다. 배포 직후 드라이런이 통과하면 곧바로 중계를 한 번 `--broadcast`로 실행한다.

### 8.3 중계 봇 운영

중계 봇은 한 번 실행하면 한 번 확인하고 끝난다. 가격이 바뀌었거나 유효기한이 2일 미만 남았을 때만 보고서를 보낸다. 가격이 바뀌었어도 마지막 변경 후 최소 간격(12시간)이 지나지 않았으면 기다린다. 플래그 없이 실행하면 무엇을 보낼지 출력만 하고, `--broadcast`가 있을 때만 BNB를 써서 전송한다.

- 중계 지갑은 `REPORTER`로 넣은 바로 그 지갑이다. 보고서 한 건마다 가스비가 드니 BNB를 조금 넣어 두고 가끔 잔액을 본다. 니모닉을 쓰면 `RELAY_INDEX`와 `RELAY_EXPECT`(그 순번 지갑의 주소)를 함께 준다. 틀리면 아무것도 보내지 않는다. 키는 저장소 밖 파일에서 읽고 출력하지 않는다.
- 타이머 예(30분마다, 본 시장). `PATH=` 줄은 crontab 맨 위에 한 번, 실행 줄은 한 줄로 쓴다.

```cron
PATH=/경로/node의/bin:/usr/bin:/bin
*/30 * * * * cd /경로/wbmb-p2p-lending && RELAY_KEY_FILE=/경로/중계키 flock -n /경로/relay.lock npm run relay:council -- --broadcast >> /경로/relay.log 2>&1
```

- **`PATH=` 줄이 필요한 이유.** cron은 로그인 셸과 달리 기본 `PATH`가 짧아 nvm으로 설치한 `node`·`npm`을 못 찾는 일이 흔하다. 그러면 스크립트가 시작되지도 않고 로그에는 `npm: not found` 같은 셸 오류만 남고 `실패:` 줄은 없다. 가격은 아무도 모르게 만료된다. `npm`만 절대 경로로 적어서는 부족하다. nvm으로 설치한 `npm`은 `node`를 `PATH`에서 찾기 때문이다. `/경로/node의/bin`은 `dirname "$(which node)"`로 확인한다. 등록한 뒤 `env -i PATH=/경로/node의/bin:/usr/bin:/bin sh -c '실행 줄'`처럼 같은 `PATH`로 한 번 실행해 본다.
- **`flock -n`이 필요한 이유.** 앞 실행이 아직 끝나지 않았는데(RPC·API가 느릴 때) 다음 실행이 시작되면 두 실행이 같은 round의 보고서를 보내려 한다. `flock -n /경로/relay.lock`은 잠금 파일을 쥔 실행이 있으면 새 실행을 곧바로 끝낸다. 이때는 로그에 아무 줄도 남지 않는다(다음 30분 뒤 실행이 이어받는다). `flock`은 util-linux에 들어 있다.
- **정상 로그는 실행마다 `카운슬 <가격> · 체인 <가격> · <사유>` 한 줄이 남는다.** 사유는 `변경 없음`, `가격 변경`, `유효기한 연장` 같은 값이다. 보고서를 보낼 때는 `보고서   round …`와 `전송됨   0x…` 줄이 더 붙는다. 마지막 `카운슬 …` 줄의 시각(파일 수정 시각)이 30분보다 오래됐거나 줄이 없으면 타이머가 돌지 않는 것이다.

- **아무것도 보내지 않고 비정상 종료(종료 코드 0이 아님)하는 경우.** 이때는 사람이 확인해야 한다.
  - 카운슬 가격 API가 15초 안에 답하지 않았거나 HTTP/네트워크 오류가 났을 때
  - API 답이 형식에 맞지 않을 때(가격이 숫자가 아니거나 0 이하, 확정 시각이 이상함)
  - 카운슬 확정 시각이 미래일 때
  - 가격이 달라졌는데 카운슬 확정 시각이 체인에 올라간 값보다 과거일 때(API가 이전 확정으로 되돌아간 경우)
  - **카운슬 가격이 체인 가격에서 30%를 넘게 떨어져 있을 때.** 컨트랙트가 한 번에 받을 수 없는 변동이다. 카운슬이 한 번에 그만큼 움직였을 때뿐 아니라, 중계가 멈춘 사이 작은 변동이 쌓였을 때도 생긴다. 오류 줄에 `카운슬 <가격> · 체인 <가격> · 한도 30%`가 찍힌다.
  - 이런 상태가 이어지면 낡은 가격을 새로 고치는 보고서도 보내지 않으므로 **온체인 가격이 만료된다**(유효기한은 최대 약 6일). 만료되면 새 체결과 가격 기반 정산이 멈추고, 연체된 대출은 8.1의 탈출구로 담보 전부가 대출자에게 넘어갈 수 있다. 타이머는 스스로 풀지 못한다. 마지막 두 경우는 아래 `--step` 절차로 사람이 푼다.
- **한도를 넘는 변동을 사람이 옮기는 절차(`--step`).** 타이머에는 절대 넣지 않는다. `--step`을 붙이면 카운슬 가격까지 한 번에 가지 않고, 체인 가격에서 한도(30%)만큼만 카운슬 가격 쪽으로 옮긴 값을 보고서로 만든다.
  1. 드라이런(전송 없음): `RELAY_KEY_FILE=/경로/중계키 npm run relay:council -- --step`. `카운슬 <가격> · 체인 <가격> · 한도만큼 단계 이동` 줄과 `보고서   round N · 가격 <보낼 값>` 줄이 나온다.
  2. **세 숫자를 손으로 확인한다.** 카운슬 가격이 카운슬 사이트(`movnvote.com`)에 지금 보이는 값과 같은지, 체인 가격이 화면에 보이던 값과 같은지, 보낼 값이 체인 가격에서 정확히 30%만큼 카운슬 가격 쪽으로 간 값인지 본다. 카운슬 가격이 이상하면(API 오류·오타로 보이면) 보내지 않고 카운슬 쪽을 먼저 확인한다.
  3. 맞으면 전송(BNB 사용): `RELAY_KEY_FILE=/경로/중계키 npm run relay:council -- --step --broadcast`. `--step`과 `--broadcast`가 함께 있어야만 나간다.
  4. 가격을 바꾼 뒤에는 최소 간격(12시간, 테스트 시장 5분)이 지나야 다음 변경을 받는다. 그 전에 실행하면 `최소 간격이 지나지 않았습니다`로 아무것도 보내지 않는다. 12시간 뒤 1번부터 다시 한다. 남은 차이가 30% 이내가 되면 `--step` 없이도 타이머 실행이 카운슬 가격을 그대로 올린다. 그때까지 타이머 실행은 계속 `실패:`로 끝나는데, 이 기간에는 정상이다.
  - **각 단계는 운영자가 중간 가격을 보증하는 행위다.** 보내는 값은 카운슬이 확정한 가격이 아니고, 보고서의 확정 시각도 체인에 있던 값을 그대로 둔다. 그 가격으로 다음 단계까지 체결과 청산이 실제로 일어난다. 내리는 방향이면 실제 카운슬 가격보다 높은 값으로 대출이 나가고, 올리는 방향이면 실제보다 낮은 값으로 청산될 수 있다. 그래서 자동으로 하지 않는다.
  - 확정 시각이 과거로 되돌아가 거부된 경우에도 값이 맞다고 확인했으면 같은 명령(`--step --broadcast`)으로 보낸다. 변동이 한도 안이면 카운슬 가격 그대로, 체인에 있던 확정 시각을 유지한 채 올라간다.
  - 가격이 이미 만료된 뒤에도 같은 절차로 되살릴 수 있다. 다만 만료된 채로 `staleSettleDelay`가 지난 연체 대출은 그 전에 누군가 정산해 담보 전부가 넘어갔을 수 있다.
- 거래를 보낸 뒤 120초 안에 확인되지 않으면 거래 해시를 출력하고 비정상 종료한다. 이때는 BscScan에서 그 거래가 처리됐는지 직접 보고, 다음 실행 전에 확인한다.
- 지갑에 BNB가 없으면 전송이 실패해 비정상 종료한다. 로그 파일에 `실패:` 줄이나 `카운슬 …` 줄이 끊겼는지 정기적으로 본다.
- 테스트 시장을 중계하려면 `--test-market`을 붙인다(`deployments/bsc-council-test.json`을 읽는다).

### 8.4 첫 실거래 점검 순서 (소액, 테스트 시장)

화면으로 만들 수 있는 대출은 **일 단위(1~365일) 기간에 유예 1일 고정**이다. 테스트 시장의 5분 최소 기간·유예는 컨트랙트를 직접 호출해야만 쓸 수 있고, 이를 대신 해 주는 스크립트는 아직 없다(`scripts/live-test.mjs`는 오라클 없는 시장만 받는다). 따라서 점검은 아래처럼 한다.

- **바로 확인할 수 있는 것:** 카운슬 가격으로 체결(담보 수량), 담보 추가와 청산 가격 변화, 상환·수령.
- **강제로 만들 수 없는 것:** 가격 하락 청산. 가격은 카운슬을 따라가므로 우리가 내릴 수 없다.
- **시간이 걸리는 것:** 연체 정산. 기간 1일 대출은 만기 + 유예 1일, 약 2일 뒤에야 정산할 수 있다.

1. 8.2의 순서로 테스트 시장을 배포하고 첫 가격을 올린다. 올라간 가격은 중계를 드라이런(`--broadcast` 없이)으로 실행하면 출력되는 `카운슬 <가격> · 체인 <가격>` 줄과 웹 화면의 가격 표시(`카운슬 확정 … · 유효 …까지`)로 확인한다. 컨트랙트 소스를 BscScan에 검증해 올리는 절차는 이 저장소에 없으므로 BscScan에서 `current`·`validUntil`을 직접 읽을 수 있다고 가정하지 않는다.
2. 대출 제안 게시(기간 1일) → 다른 지갑으로 일부 체결 → 담보 수량이 화면의 가격과 맞는지 확인.
3. 담보 추가 → 대출 카드의 청산 가격 변화 확인. 일부 상환·전액 상환·담보와 USDT 수령도 이 단계에서 확인할 수 있다.
4. 갚지 않은 대출 하나를 남겨 두고 만기 + 유예 1일(약 2일)이 지난 뒤 정산 → 대출자가 부채 + 5%만큼의 WBMB만 받고 나머지가 차입자에게 돌아오는지 확인.
5. 정산 후 두 지갑이 각자 WBMB를 수령, 컨트랙트의 보유량과 장부 부채가 0인지 확인.

**테스트 시장의 중계를 멈추기 전에 테스트 대출을 모두 끝낸다**(상환하거나 정산한다). 테스트 시장은 가격 중단 대기가 5분이다. 중계를 멈춰 가격이 만료되면, 유예가 이미 지난 대출은 만료 5분 뒤부터(유예가 남은 대출은 유예 종료 5분 뒤부터) 누구나 정산해 담보 전부를 대출자에게 넘길 수 있다. 본 시장의 7일과 달리 손쓸 시간이 없다.

이 점검을 마치고 사용자가 지시한 뒤에만 본 시장(새 수수료 지갑, 전용 중계 지갑)을 배포하고 중계 타이머를 켠다.

### 8.5 남는 위험

- **중계 신뢰.** 서명 키를 가진 사람이 변동 한도(한 번에 30%, 12시간마다) 안에서 가격을 정한다. 키가 새면 가격을 내려 청산을 유발하거나 올려 담보 부족 대출을 받을 수 있다.
- **가격 API 서버.** 중계 봇은 `movnvote.com`의 응답을 그대로 서명해 올린다. 그 서버(또는 그 도메인·통신 경로)를 장악한 사람은 키 없이도 같은 한도 안에서 키를 가진 사람과 똑같이 가격을 움직일 수 있다. 봇이 걸러 내는 것은 형식 오류, 미래의 확정 시각, 한도를 넘는 값뿐이다.
- **보냈지만 채굴되지 않은 보고서.** 서명해 전송했는데 블록에 들어가지 않은 보고서는 그 round가 채워지기 전까지 유효하고, 서명만 있으면 누구나 제출할 수 있다. 다음 실행이 같은 round로 새 보고서를 만들기 전에 누군가 예전 보고서를 넣으면 그 가격이 올라가고, 값이 달랐다면 `minInterval`(12시간) 동안 새 가격으로 바꿀 수 없다. 즉 가격 변경이 최대 12시간 늦어질 수 있다. 예전 보고서도 운영자가 서명한 값이고 유효기한이 지나면 쓸 수 없으므로 임의의 가격이 올라가는 것은 아니다. `확인되지 않았습니다`로 끝난 실행은 그래서 직접 확인한다.
- **한도를 넘는 변동.** 카운슬 가격이 체인 가격에서 30% 넘게 벌어지면 타이머는 멈추고 사람이 8.3의 `--step` 절차로 옮겨야 한다. 제때 하지 않으면 가격이 만료된다. 옮기는 동안의 중간 가격은 카운슬 가격이 아니다.
- **비표준 게시글.** 화면은 표준 조건의 게시글만 보여 주지만 컨트랙트는 다른 담보 여유·청산선도 받는다. 화면 밖에서(직접 호출, 다른 화면) 체결하면 청산선이 훨씬 가까운 대출이 될 수 있다.
- **느린 가격.** 급락 때 카운슬 가격이 며칠 높게 남아 그 사이 청산되면 대출자가 받는 WBMB의 실제 가치가 부채보다 작을 수 있다. 5% 보너스와 게시자의 담보 여유로만 완화된다.
- **환금성.** 받은 WBMB를 팔 시장이 얕아 큰 수량은 가격을 밀면서 팔게 된다.
- **봇 중단.** 가격이 만료되면 새 체결과 가격 기반 정산이 멈추고, 멈춘 사이 가격이 급락하면 청산이 제때 안 된다. 연체 대출은 8.1의 탈출구로 풀리지만 그때는 담보 전부가 대출자에게 간다.
- **`REPORTER` 오류.** 틀린 주소로 배포하면 가격을 받을 수 없는 시장이 되고 고칠 수 없다.
- **불변.** 배포 후 보고자·한도·수수료·보너스를 바꿀 수 없다. 바꾸려면 새 배포이고 기존 대출은 옛 시장에서 끝내야 한다.
- **컨트랙트가 증명하지 않는 것.** 보고자가 카운슬 가격을 그대로 옮겼는지, 카운슬 가격 1달러가 1 USDT인지, WBMB 1개가 BMB 1개인지는 컨트랙트가 알지 못한다.
- 감사 없음, WBMB 추가 발행, 토큰 관리 권한 등 7절의 위험은 그대로다.
